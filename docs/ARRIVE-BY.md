# 按到达时间规划与最佳出门时间（Arrive By）

## 1. 现有路由器的时间语义（复用基础）

- 时间单位是**服务日 0:00 起的秒**；`parseClock('HH:MM')` 得到分钟，00:00–03:59 自动记为次日
  （`h+24`），因此跨午夜班次（`minute > 1440`）与截止时间 `00:15` 可以直接比较。
- 状态是 `(station, line)`；转移只有两种：
  - **乘车**：从当前状态取该线该方向 `depart > 当前时刻` 的最多 40 个班次，坐到其任一后继站；
  - **换乘**：同站换到另一条线，耗时 `base / (speed·sprint) + bufferSec`，同线不产生换乘边。
- 起点在 `startSec` 时对出发站的每条线各放一个初始状态（等价于「已到站台」）。
- 到达时刻 = 目的站**站台**时刻，不含出站步行。

因此「Arrive By」不能简单用 `deadline − 估计时长`：它与列车发车时刻离散相关，且截止时间
约束的是**出站后的目的地时刻**。

## 2. 门到门模型

四段互不重叠，避免重复计时：

| 段 | 字段 | 说明 |
| --- | --- | --- |
| 家 → 首乘站台 | `toPlatformSec` | 含进站、安检、闸机、站内步行 |
| 到站站台 → 目的地 | `fromStationSec` | 含出站、闸机、站外步行 |
| 进站/换乘安全余量 | `safetySec` | 加在每次上车前；同时作为路由器的 `bufferSec` |
| 步行不确定性 | `walkJitterSec` | 只影响推荐窗口与风险等级，不参与可行性判定 |

给定离家时刻 `t`，等价的路由起点是 `t + toPlatformSec + safetySec`：
路由器只上「发车晚于该起点」的车，于是「到站台后至少留 `safetySec`」被严格保证。
到达目的地的时刻是 `站台到达 + fromStationSec`，**截止时间与它比较**。

## 3. Arrive By 算法

### 3.1 单调性

对同样的出发/到达站与日期，`plan(from,to,start)` 的到达时刻随 `start` 单调不减：
任何从更晚时刻可行的行程，从更早时刻出发都可以原样等待后执行。因此
「能在 `deadline` 前到达」的离家时刻集合是一个区间 `[…, t*]`。

### 3.2 二分求最晚出门

```
upper = deadline − fromStationSec − toPlatformSec − safetySec
lower = deadline − maxSearchSec（默认 4 小时）
若 upper 可行 → t* = upper
否则若 lower 不可行 → 无解（不编造方案）
否则在 [lower, upper] 上二分，取最大的可行整数秒
```

每次判定调用一次 `planAtSeconds`，判定次数 `O(log 搜索窗口)`（秒级精度约 16–18 次），
不做逐分钟枚举。`planAtSeconds` 是 `plan()` 抽出的秒级入口，语义完全一致。

### 3.3 候选与目标分离

在推荐窗口 `[recommended − windowSec, recommended]` 内，以**真实首乘发车时刻**为锚点
（`t = depart − toPlatformSec − safetySec − 1`，严格早 1 秒保证能上这一班），逐个评估，
再加理论最晚与推荐方案，去重后做 Pareto 过滤（到达更早、出门更晚、站台等待更少），
最后分别选出：

- **最早到达**：`arrivalDoor` 最小；
- **最晚出门**：`doorExit` 最大；
- **等待最少**：`platformWait + transferWait` 最小；
- 其余按到达时间补充，要求首乘班次或到达时间有明显区别。

三个目标各自保留、不合并成加权分数；界面用「同样 X 前到达，可以晚出门 N 分钟」解释差异。

### 3.4 推荐窗口与风险

- 理论最晚 `t*` 往往刚好卡在截止时间，余量为 0，**不能直接当推荐**。
- 推荐出门用第二次二分求得：把 `walkJitterSec` 当作必须留出的到达余量，
  即以 `deadline − walkJitterSec` 为新的截止时间再求最晚出门 `t_rec`；
  于是按推荐时间出门，即使步行多花掉全部不确定性，也能在截止前到达。
- 若更早的时段内已无车（`t_rec` 不存在），退回 `t*` 并在风险里明确提示。
- 窗口 = `[t_rec − windowSec, t_rec]`（默认 2 分钟）。
- 风险按**推荐方案**的到达余量：`safe`（≥5 分钟）/ `tight`（2–5 分钟）/ `risky`（<2 分钟）；
  理论最晚方案余量不足 1 分钟时附加「会压线到达」提示。
- 到达余量不足时只提示提前出门或调整参数，**不会悄悄放宽 `safetySec`**。

## 3.5 出发模式的窗口搜索

`searchDepartures()` 复用同一套门到门模型：在 `[start + toPlatform + safety, +windowSec]`
（默认 30 分钟）内枚举真实首乘班次，各评估一次，输出最早到达 / 最晚出门 / 等待最少，
同样不做加权评分。界面在「按出发时间」下展示这组方案。

## 4. 为什么不用反向时刻表路由

反向搜索的状态应是 `(station, line, 最晚可上车时刻)`，转移需从「必须在某时刻前到达」反推，
同时要处理换乘步行、安全余量与跨午夜，和现有前向 Dijkstra 是两套正确性证明。

第一版选择「前向 `planAtSeconds` + 单调二分」，正确性直接复用已测试的路由器，
代价是每次判定一次完整 Dijkstra。实测北京路网（28 线 / 19,844 班次）：

| 场景 | 耗时 | 规划次数 |
| --- | --- | --- |
| 西直门 → 国贸 09:00，窗口 10 分钟 | ~90 ms | 39 |
| 同上（含推荐余量二次二分与 30 分钟候选） | ~180 ms | 60 |
| 同上，窗口 30 分钟 | ~145 ms | 84 |
| 天通苑北 → 亦庄火车站，窗口 30 分钟 | ~167 ms | 36 |
| 苹果园 → 环球度假区，窗口 30 分钟 | ~192 ms | 39 |

若后续需要更低延迟，可在不改语义的前提下把「候选首乘班次枚举」改成反向扫描，
或用 Worker 承载计算；当前先保证正确性。

## 5. 正确性测试（构造性）

`packages/core/test/arrive-by.test.ts` 用内联小网络逐条验证：

1. 同一班车晚出门只减少站台等待，到达不变；
2. 截止时间恰好可达 / 提前 1 分钟不可达；
3. 截止时间约束目的地而非列车终点；
4. 首班车之前无解，最晚出门受末班车约束；
5. 换乘步行 60 秒可行，600 秒即不可行；
6. 进站 10 分钟、出站 5 分钟完整计入耗时与截止时间；
7. 错过首乘的晚到分钟数；
8. 三次乘车两次换乘、短交路不坐过终点、跨午夜服务日；
9. 同线被截断的两段（模拟关联不确定）不会拼成一次乘车；
10. 无解时 `latest/recommended/alternatives` 全为空；
11. 最早到达 / 最晚出门 / 等待最少各自可取，且评估次数有上界；
12. 同站出发到达直接说明无需乘车。

## 6. 限制

- 全部基于计划时刻，不预测实时延误，不构成运营保证。
- 站外步行时间为用户手动输入；未来接高德步行 API 时应作为可替换提供者，
  先算出 `toPlatformSec/fromStationSec` 再传入，核心算法不做网络请求。
- 长春数据的不确定关联已在数据层截断，本模块不会把截断区段当作连续车次。
