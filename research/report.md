# 北京 / 长春轨道交通「逐班时刻表换乘优化器」可行性研究报告

- 调研日期：2026-10-30
- 调研范围：北京地铁、长春轨道交通；四个开源项目；官方 App / 网站 / 公共数据平台；公开实时接口
- 配套原型：本仓库（Vue 3 + Pinia + TypeScript PWA）

## 0. 结论摘要

| 问题 | 结论 | 依据 |
| --- | --- | --- |
| 北京能否做逐班换乘优化？ | **可以，但仅限「计划时刻」级** | 京港地铁官网直接发布逐班到站时刻表图片；第三方汇总已结构化 28 条线 |
| 北京能否做实时赶车？ | **目前不能** | 未发现公开、文档化、允许第三方调用的实时列车 API |
| 长春能否做逐班优化？ | **已全量导入，开放计划级查询** | E 出行 H5 table2 全量：8 线/142 站/4,943 条已确认区段；站-线覆盖 100%；相邻站关联覆盖 99.7% |
| 换乘步行时间是否可靠？ | **不可靠，只能作估计** | 开源数据为爱好者整理/推算；非运营方实测 |
| 是否值得继续开发？ | **值得做北京计划级 MVP** | 数据覆盖、算法与前端均可在纯前端完成；实时与长春需另寻数据合作 |

**一句话**：北京与长春都可以做「不承诺实时、但逐班可解释」的换乘决策工具；长春数据由 table2 全量导入，车次是相邻站时刻唯一匹配推断，关联不唯一的区段不上车，因此结果偏保守。任何声称「实时赶车」的实现，在当前公开数据条件下都应视为过度承诺。

## 1. 数据粒度：先分清五种东西

| 粒度 | 定义 | 北京 | 长春 | 本原型 |
| --- | --- | --- | --- | --- |
| 首末班时刻 | 每站每方向首班/末班 | 官方有（HTML/图片） | 官方有（图片，分夏冬季） | 已覆盖 |
| 行车间隔 | 高峰/平峰发车间隔 | 官方公告/时刻表可推导 | 官方公告可查 | 由逐班数据自然体现 |
| 完整逐班时刻 | 每一班车在每个站的到站时刻 | 京港官网图片直接核验；其余线路依赖第三方整理 | E 出行 H5 table2 全量导入 | 北京 28 线、长春 8 线均已导入 |
| 预测到站 | 基于历史/位置的预计到站 | 高德/百度等 App 内有，无开放接口 | 同类 | 未使用 |
| 真实实时 | 实际列车位置/到站 | 官方 App 内有，无公开 API | 官方 App 内有，无公开 API | 未使用 |

关键区别：**「有实时功能」不等于「有开放实时 API」**。官方 App 的内部接口、网页 XHR、小程序请求都不应默认视为允许第三方使用的开放 API。

| [BoyInTheSun/beijing-subway-schedule](https://github.com/BoyInTheSun/beijing-subway-schedule) | CC BY-SA 4.0 | 2026-01-13（`schedule.json` 提交） | JSON，10.3 MB | 北京 28 条线（含机场、西郊、亦庄 T1 等） | 完整逐班，按工作日/双休日 | **可用**；需遵守 ShareAlike，注意汇总滞后 |

### 2.2 BoyInTheSun/beijing-subway-schedule

- 数据结构：`{工作日|双休日: {线路: {方向: {虚拟车号: [[站名, "HH:MM"], ...]}}}}`，即每班车在各站的到站时刻。
- 规模：`train_schedule_all/schedule.json` 10.3 MB；工作日 28 条线。示例：4 号线大兴线工作日南行 332 班、北行 321 班；2 号线外环 214 班、内环 216 班。
- 来源：README 明确为北京地铁、京港地铁官网公布的**到站时刻表图片**，经 OCR 和人工纠错；处理代码与中间文件未开源。
- 更新：`schedule.json` 最后提交 **2026-01-13**；此前 2025-12-29、2025-09-25。属于不定期更新。
- 许可：CC BY-SA 4.0，衍生数据需同许可共享。
- 风险：
  - OCR 与人工纠错不可避免；README 自己承认官方时刻表也有错误。
  - 汇总文件可能滞后于底层线路文件；例如 Beijing-Subway-Tools 的 1/2/5 号线文件标注截止 2026-05/07，而汇总 JSON 最后提交是 2026-01。
  - 只有工作日/双休日两套图，无节假日专用图、临客、临时调整。

### 2.3 Mick235711/Beijing-Subway-Tools

- 数据：`data/beijing/*.json5`，28 个线路文件；采用 `{first_train, delta}` 压缩表示发车间隔，需工具展开，不能直接当逐班表读取。
- 附加数据：`metadata.json5` 含 8 座换乘站的步行时间（分钟、距离、楼梯）、`station_spacing`、票价规则、车厢类型；另有 `line1` 等文件头标注数据截止日期（1 号线 2026-05-19，2/5 号线 2026-07-23，4 号线 2025-01-10）。
- 许可：MIT（代码与数据）。
- 风险：人工维护；换乘时间为爱好者整理/推算，不是运营方实测；不同线路数据日期不一致；无实时。

### 2.4 JamesZBL/subway-finder

- 仓库无 LICENSE 文件，GitHub API 返回 `license: null`。按默认版权规则，**不能直接复制、修改或再分发**。
- `subway-finder/src/data/timetable.js` 只有 4 号线：每站 `{firstTrain, lastTrain, stopTime}`，没有逐班时刻。
- 代码用「首班 + 每站默认 3 分钟」生成中间班次（源码注释写明「每站默认 3 分钟」），属于**合成数据**，不能冒充正式时刻表。
- 结论：仅可参考「实时位置可视化 + 用户采集」的产品思路，不可用作数据源。

### 2.5 Naptie/openmetro

- 规模：`data/` 下 37 个城市网络，含 `cn-beijing`、`cn-changchun`；标准化为 `lines/stations/stops/patterns/segments/transfers/timetables/fares`。
- 北京：`timetables.json` 1004 条记录，粒度是**每站每方向每目的地的首末班**，不是逐班；`segments.json` 有官方区间运行时间；`transfers.json` 256 条。
- 长春：8 条线、142 站、26 座换乘站（5 号线 2026-09-28 开通，6 号线 2026-03-28 开通）；`timetables.json` 生成于 2026-10-22。
- 重要发现：北京 `transfers.json` 的 `source_id` 与 `extras.walk_source` 均为 `baidu-transit`，即换乘步行来自百度路径规划的建模值；但 `network.json.quality.transfer_times.precision` 标为 `official`。**质量标注与来源不一致**，不能把该字段当作运营方实测。
- 长春 `network.json` 的 notes 明确：官网仅以图片发布时刻表，未做 OCR；逐站首末班取自百度 `direction/v2/transit`，官网接口仅作兜底；冬季/工作日差异只存在于图片中，机器可读源无法区分。
- 提供只读 REST API、OpenAPI 文档、CORS 开放；但**不含实时数据**。
- 许可：MPL-2.0（文件级 copyleft）。

## 3. 官方与平台数据源

### 3.1 北京

**京港地铁官网（直接核验）**

- 首末班页：`https://www.mtr.bj.cn/service/line/timetable/line-4.html`
- 各站时刻表页：`https://www.mtr.bj.cn/service/line/line-4.html`
- 页面内 `schedule.remarks` 写明「以下列车时刻表计划于 2024 年 9 月 1 日首班车起开始执行」，并以 JPG 图片给出每站每方向**每一班**的到站时刻，区分工作日/双休日。
- 示例图片（4 号线北宫门，开往安河桥北，工作日）：
  `https://cdnwww.mtr.bj.cn/bjmtr/station/U5za1h-MCsXvTZWwQmCE5.jpg`
- 图片底部注明「列车时刻表仅供参考，实际以现场列车运行情况为准」。
- 结论：**北京确实存在官方逐班数据**，但形态是图片，不是结构化接口；第三方 OCR 是当前唯一低成本结构化路径。

**北京地铁官网（未能核验）**

- 本次网络环境无法解析/连接 `www.bjsubway.com`（DNS 返回代理地址，TLS 握手失败），因此未能直接核验北京地铁运营公司线路的官方时刻表页面。
- 1/2/5 号线的逐班数据在本次调研中只能依赖 BoyInTheSun 的第三方整理，属于「第三方声称来自官网图片」，不是本次直接核验。

**北京市公共数据开放平台（直接核验）**

- 平台：`https://data.beijing.gov.cn/`
- 使用站内搜索接口检索：
  - `name=地铁` → 3 条：等级景区交通信息、西城区地铁站名单、西城区地铁游名单；
  - `name=时刻表` → 0 条；
  - `name=地铁时刻` → 0 条；
  - `name=轨道交通` → 3 条，均非时刻表（施工企业信用评价、城市概况、残联设施点位）。
- 结论：**未发现**地铁逐班时刻表数据集。即使存在需登录/申请的数据，也不能视为开放 API。

**官方 App**

- 「亿通行」：扫码乘车、出行服务；未发现公开开发者文档。
- 「北京地铁」官方 App：刷码乘车、线路规划、票价、延误证明等；未发现公开 API。
- 官方 App 内的到站信息不构成第三方可用的开放接口。

### 3.2 长春

**长春轨道交通官网（直接核验）**

- 公告：《长春轨道交通各线路首末班及换乘时间表（2026 年 9 月 28 日）》
  `http://www.ccqg.com/ccgdjtgxlsmbjhcsjb2026n9y28r.html`
- 公告以 8 张 JPG 图片发布：逐站首末班、上行/下行、夏季（5/1–10/31）与冬季（11/1–次年 4/30）两套运营时间；并含换乘时间表。
- 示例图片：`http://www.ccqg.com/ueditor/php/upload/image/20260928/1790578892517480.jpg`
- 没有逐班时刻，也没有结构化下载。

**官网内部接口（不是开放 API）**

- `POST http://www.ccqg.com/api/v1/getLines` 返回各线、各站的首末班字段，可访问，但：
  - 未文档化、未授权第三方使用；
  - 字段存在陈旧/错误（openmetro 的 notes 指出 2/3/4 号线 `standnumber` 与实际站数不符、4 号线 `endstand` 仍是已废弃站名、7/8 号线首末班窗口相同等）；
  - 只有首末班，没有逐班。
- 因此不能把它当作稳定数据源，更不能据此做「赶车」。

**长春 E 出行 H5**

- App Store 信息：长春市轨道交通集团开发，版本 1.0.23；描述为扫码乘车/电子车票。
- H5 的 `table2` 接口已实测：按 lineCode/standCode/direction/weekday 请求单站时刻；`startInterval` 为小时，`paramsList[].time` 为分钟。
- 未发现公开开发者文档、开放 API 或再分发许可；只做少量、串行、限量的协议验证，不把它当开放 API 批量采集。

### 3.3 实时数据接口

- 官方渠道：北京地铁/京港地铁/长春轨道交通的 App 与官网均未提供公开、文档化的实时列车 API。
- 北京 MaaS（高德/百度）有实时公交、满载率等功能，但属于商业合作/App 内能力，未发现面向第三方的公开接口。
- 高德/百度开放平台：本次网络环境无法访问高德文档域名（解析到非公网地址），未能逐项核验；公开 Web 服务以路径规划为主，实时公交到站通常需要申请/商务授权。**结论保持为「未发现可直接调用的公开实时列车接口」**，而不是断言「绝对不存在」。
- 结论：原型不接入任何实时接口，UI 明确标注「非实时」。

## 5. 可行性判断

### 5.1 北京：计划级可行，实时级不可行

**可行部分**

- 有官方逐班图片（京港直接核验），有第三方结构化（28 线、工作日/双休日）。
- 时间依赖网络、最早到达、保守/冲刺对比、下一班损失都可以在纯前端完成。
- 28 条线、425 站、19,844 班全量导入后，数据 3.41 MiB（gzip 后约 1.1 MiB），手机端可离线加载。

**不可行/不能承诺**

- 不能承诺「实时」：没有公开实时 API；计划时刻遇到延误、临客、限流就会失真。
- 不能承诺「官方精确换乘步行」：现有换乘时间是爱好者估计；西直门 2→4 号线仅 30 秒，明显偏短。
- 不能覆盖节假日专用图：数据只有工作日/双休日两套。
- 1 号线 BST 站表含已关闭的苹果园、缺八角游乐园；17 号线望京西未在班次中停靠。原型按汇总班次为准，逐线标记 `review`，不补造班次。
- 6 号线存在通过不停车与待避记录；2/10 号线为环线，班次在端点折返，闭环段依赖反方向列车。

### 5.2 长春：table2 全量已导入，可做计划级查询

- 官网只有首末班 + 换乘时间图片，没有完整逐班时刻。
- E 出行 H5 的 `table2` 接口已实测确认：`startInterval` 是小时，`paramsList[].time` 是分钟；请求体为 `{lineCode, standCode, direction, weekday}`。
- 全量数据：8 条线、142 个唯一车站/168 个线路-车站对、4,943 条已确认区段（整线 4,660）；站-线覆盖 **168/168 = 100%**。
- 相邻站关联覆盖 **97,267/97,594 = 99.7%**；关联不唯一的腿 **15/640 = 2.3%**，这些腿断开、不写入车次；状态 `ready`，已生成正式 `network.json`，PWA 可切换长春查询。
- 分段验证：21 组 unique、11 组 partial、0 组 insufficient；31 条真实中途终到被保留，71 条已确认区段因不确定关联被迫截断。
- `weekday` 实测：0、3–7 返回空 list；1/2 有数据，1 的班次更密（176 vs 139）。导入器把 1/2 解释为工作日/双休日，但标记为推断，需 App/官方文案复核。
- 原始响应与导入快照默认不公开再分发；本次全量采集已在用户明确要求下完成。

### 5.3 会改变结论的条件

- 北京/长春运营方发布结构化 GTFS/GTFS-RT 或官方开放 API；
- 或建立可持续的 OCR + 人工校验流水线，并把更新责任、误差范围写进产品；
- 或与高德/百度/运营方签订实时数据合作。

## 6. 最小原型设计与实现

### 6.1 技术架构

- Monorepo：`packages/core`（算法与数据，与框架无关）+ `apps/web`（Vue 3 + Pinia + TypeScript + Vite PWA）。
- **纯前端，无后端**：数据构建期裁剪，查询在浏览器内完成；Service Worker 预缓存，离线可用。
- 构建产物约 3.68 MB JS（gzip 1.14 MB），数据 3.41 MiB；全网单次查询约 **3–26 ms**（含两套方案与逐换乘分析，随换乘次数变化）。

### 6.2 数据管线

`scripts/build-data.mjs`：

1. 读取 `schedule.json`，导入全部 28 条线；每条线同时读取 BST 线路文件，记录站表、方向、截止日期与完整性；
2. 统一站名（去掉 `木樨地(1号线)` 一类后缀），按汇总班次建立实际服务站点；
3. 解析 6 号线特殊标记：`(HH:MM` 为通过不停车（从可上下车站序剔除），`HH:MM-` 为待避（保留到站时刻，发车未知，保守处理）；
4. 时刻转服务日分钟（跨零点加 1440）；大小为交路、短交路、机场线、环线均按实际车次保留，不补班；
5. 从 BST `metadata.json5` 提取 104 座换乘站、221 条原始记录；同一线路对的方向/时段变体全部保留，缺失线路对按 180 秒补齐并标 `fallback`；
6. 逐线计算站表缺口、额外站、缺失相邻区间、越行/待避计数，写入 `line.status` 与 `line.notes`；
7. 输出 `packages/core/src/data/network.json`（3.41 MiB，28 线/425 站/19,844 班/299 个换乘变体）。

### 6.3 算法

- 节点：`(station, line)`；边：
  - 乘车边：某一班车从 A 站到后续 B 站，权为到站时刻；
  - 换乘边：同站从 line A 步行到 line B，权为 `base ÷ 步速 + 安全余量`；
  - 同一线路对存在方向/时段多个变体时取**保守上界**，避免因方向不明而低估；西直门 2→4 的 30 秒原值保留，并附测量条件说明。
- 最早到达：时间依赖 Dijkstra；到站后二分查找下一班可坐车次；严格判定「发车时刻 > 到达+步行」，避免把 0 秒余量当可乘车。
- 保守方案：正常步速；激进方案：1.35× 步速，各跑一次。
- 逐换乘分析：
  - 余量 = 发车时刻 −（到达 + 步行 + 余量）；
  - 冲刺可赶：在「正常走赶不上、冲刺能赶上」的前一班中，取全程收益最大者；
  - 错过损失：乘下一班到原下车站，再从该站重新规划到终点，得到预计晚到。
- 缺失/无车：返回明确原因，不补造班次；缺换乘数据时用 180 秒并标 `fallback`。
- 用户实测：换乘卡片可录入 0–1800 秒的个人步行时间，存 localStorage，优先于整理值并标 `user`；修改后自动重算。

### 6.4 产品

- 输入：出发站、目的站、时间、日期类型（工作日/双休日）、步速（0.8–1.3×）、换乘安全余量（15–90 秒）。
- 输出：到达时刻、全程时长、换乘次数；保守/冲刺两个标签页；逐段乘车与步行；每个换乘的余量、可赶的前一班、错过的下一班；换乘来源/可信度/风险；数据提示。
- 交互：425 站可搜索选择器；28 条线覆盖状态面板；换乘卡片可记录个人实测；`localStorage` 持久化。
- PWA：可安装、离线；无地图、账号、AI 聊天。
- 覆盖：北京 28 条线、425 站；UI 明确写「非实时」「汇总 2026-01-13」，逐线日期在覆盖面板。

### 6.5 验证

- 23 个单元测试：全量数据完整性、28 线双向可达、1 号线全程、6 号线越行区段、房山/燕房支线换乘、环线、机场线、跨午夜、末班失败、换乘建议、个人实测、性能。

- 全网单次查询 3–26 ms（测试机 Node 24）。

## 7. 风险与后续建议

### 7.1 当前风险

1. **数据新鲜度**：汇总 JSON 最后 2026-01-13，底层线路文件有 2026-05/07 的更新，二者可能不同步；产品必须显示版本，不能假装最新。
2. **换乘时间误差**：西直门 2→4 号线 30 秒原始记录 distance 0、stairs 37、无方向条件；反向 4→2 为 2.5 分钟/100 米/86 级台阶。已保留原值并提示“疑为局部测量”，未认定错误、未自动改写。复兴门/建国门存在高峰/平峰不同走法，原型取保守上界。
3. **许可**：CC BY-SA 4.0 有 ShareAlike，商业化需评估；subway-finder 无许可证，不能复用。
4. **节假日**：无专用图；节假日按双休日跑会偏差。
5. **站表差异**：1 号线 BST 站表含苹果园、缺八角游乐园；14 号线汇总有陶然桥、BST 未列；17 号线望京西未停靠。以上均逐线标 `review`，原因显示在覆盖面板。
6. **6 号线越行/待避**：通过不停车已剔除，但待避列车发车时刻未知，按到站时刻保守处理，可能低估可赶上的班次。
7. **环线与换乘缺口**：2/10 号线闭环段依赖反方向；78 个同站线路对缺少换乘时间，按 180 秒默认估计。

### 7.2 建议

- 短期：补齐长春换乘步行时间；对 15 段关联不唯一的相邻站（多在 1/2/3/4 号线首末段与 6 号线端部）做人工抽查；加入「末班车赶不上」提示。
- 中期：把数据管线做成可重复的 CI（下载图片→OCR→人工校验→版本对比）；输出 GTFS 供其他工具复用。
- 长期：只有拿到官方结构化时刻/实时接口，才做「实时赶车」；否则保持「计划时刻 + 明确免责声明」。

## 8. 长春 E 出行 table2 离线导入（二期）

- 当前状态：8 条线、142 个唯一车站/168 个线路-车站对、4,943 条已确认区段；站-线覆盖 **168/168 = 100%**；相邻站关联覆盖 **99.7%**，关联不唯一 **15/640 段**；`ready`，已生成正式 `network.json` 并接入 PWA。
- 协议：
  - 线路：`GET http://app.ccetravel.cn/micro/other/train/time/get/subwayLine/lines`
  - 逐站：`POST http://app.ccetravel.cn/micro/other/train/time/get/table2`
  - 接口实际返回 **JSON**（并非 XML）；已移除 XML 解析依赖。
  - `startInterval` 小时 + `paramsList[].time` 分钟；方向端点、站码、`firstDate`/`lastDate` 均参与校验。
- `weekday` 实测证据：0、3–7 空；1/2 有数据；1 比 2 班次密。解释为工作日/双休日属于推断，导入器显式标注，不写成官方定义。
- 离线导入器：`tools/changchun-import/import-table2.mjs`，只读 `data/changchun/raw/`，不发起网络请求；输出逐站时刻、匹配报告、`network.partial.json`、`current.json` 与版本快照。
- 车次匹配：
  - 相邻站采用单调最大基数匹配，运行时间窗口 1–5 分钟。实测 640 条腿的时刻差主峰为 1–4 分钟；窗口放宽到 15 分钟会把与发车间隔同余的 8–9 分钟错位对齐当成候选，制造大量本不存在的多解。
  - 关联确定性逐对判定：把某个配对禁用后最大基数下降，才说明「所有最大匹配都包含它」；只有这类配对写入车次。路径计数会把「先跳 A 再跳 B」与「先跳 B 再跳 A」算成两条，只能当快速筛子，不能当唯一性证明。
  - 关联不唯一的腿整段断开，但两侧已确认区段保留：真实中途终到（31 条）不会被误删，被迫截断的区段（71 条）单独计数。
  - 车次数是**已确认区段数**，不是实际开行班次；汇报时只能说数量覆盖，不能说「配对正确的概率」。
  - 缺站/跳站时缺口两侧不跨站匹配。
  - 闸门：站-线覆盖 ≥95%、相邻站关联覆盖 ≥90%、关联不唯一腿 ≤10%，且每组 `verification` 不为 `insufficient`、`gaps` 为空；不满足只生成 partial，不进入正式路径搜索。
- 版本与回退：每次 build 生成独立版本；`rollback <version>` 只切换 `current.json` 指针，不删除历史。
- 请求策略：先做 11 次协议验证；用户明确要求后，完成 672 个站点/方向/日类型组合的串行采集（含既有样本），默认 3–5 秒、后经用户授权约 1 秒；遇超时停止并断点续跑，未绕过任何限制。
- 合规：原始响应与导入快照默认被 `.gitignore` 忽略；派生时刻表已按用户要求接入 PWA。E 出行数据使用条件未确认，公开部署前需确认许可。维护步骤写成 agent skill：`skills/changchun-data-maintenance/SKILL.md`，不再内置 OCR/截图流程。
- 采集范围：已完成 8 条线、168 站、2 方向、2 日类型（672 个组合，含既有样本）；后续按调图/版本更新重跑。
